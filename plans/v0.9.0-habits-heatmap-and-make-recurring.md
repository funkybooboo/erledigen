# Plan: habit heatmap + "make recurring" toggle

Two remaining small items from the v0.9.0 habits slice (roadmap lines
765-770): the habit detail heatmap and the promote-to-recurring toggle.
Deliberately excludes the bigger v0.9.0 remainder (Kanban board, summary
sections, holidays) -- those are separate slices.

---

## Context (verified against main at 5c4308f)

- `RecurringTaskStats` (packages/shared/src/types/recurringTask.ts:33)
  carries only aggregates. The heatmap needs per-day completion data.
- Server stats: `RecurringTaskService.computeStats`
  (packages/server/src/services/RecurringTaskService.ts:95) already
  loads every instance via `taskRepo.findByRecurringTaskId(id)`, builds
  `occurrences` ({date, completed}), and recomputes on every read.
  Persistence (`upsertStats`) only stores the four aggregates.
- Client: `recurringTaskStore.fetchStats` caches stats in a SvelteMap;
  `HabitsModal.svelte` lists habits with streak badges + a create/edit
  form, but has no habit detail view.
- `UpdateTaskSchema` intentionally excludes `recurringTaskId` /
  `instanceDate` from public input (openapi/schemas/inputParity.test.ts),
  so promoting a task must be server-side.
- Task query API has no `recurringTaskId` filter
  (openapi/schemas/task.ts TaskQuerySchema) -- another reason not to
  build the heatmap from client task queries.

## Design decisions

1. **Heatmap data: extend `RecurringTaskStats` with `completedDates:
   string[]`** (sorted ISO dates of completed occurrences, bounded to
   the trailing 364 days). Computed in-memory in `#computeStats` from
   the already-loaded occurrences; NOT persisted (the sqlite row keeps
   the four aggregates only -- no migration, and steady-state reads
   stay no-write). One fetch gives the modal the streak badges AND the
   heatmap. Alternative rejected: a separate history endpoint (extra
   round trip, no consumer besides the heatmap).
2. **Promote flow: server-side adoption endpoint.** `POST
   /api/recurring-tasks/adopt` with `{ taskId, schedule fields }`. The
   server creates the template from the task's text/tags/notes, stamps
   the task itself as the first instance (`recurringTaskId`,
   `instanceDate = task.date`), and generates the remaining instances
   through the standard horizon. The task is never deleted -- it IS the
   first instance. Demotion is out of scope (deleting the habit already
   keeps instances; roadmap does not ask for un-promote).
3. **Heatmap component is standalone + Storybook'd** so it can be
   reviewed in isolation (project convention: every component has a
   `.stories.ts`).

## Slice 1 -- habit detail + heatmap

Server (packages/server):

1. `shared`: add `completedDates: string[]` to `RecurringTaskStats`.
   - The sqlite repo's `findStats` returns the stored aggregates; give
     it a sensible `completedDates: []` there and let the service layer
     overwrite with computed values, OR keep the repo return type
     narrow (preferred: introduce the field on the shared type and
     have `SqliteRecurringTaskRepository.findStats`/`InMemory` return
     the aggregates with `completedDates` filled by the service).
     Decide when touching the contract tests
     (adapters/data/contracts/recurringTaskRepositoryContract.ts).
2. `RecurringTaskService.#computeStats`: build `completedDates` from
   completed occurrences (filter to the trailing 364 days from
   dateProvider.today()), include in the returned stats. The
   unchanged-row check ignores this field (it is derived, not stored).
3. Unit tests: extend `RecurringTaskService.test.ts` -- completedDates
   ordering, 364-day bound, empty for a fresh habit.
4. Bruno: extend the existing `Get RecurringTask Stats.bru` to assert
   the new field; OpenAPI schema
   (openapi/schemas/recurringTask.ts:82 area) gains the field so the
   spec stays truthful.

Client (packages/client):

5. New `HabitHeatmap.svelte` component:
   - Props: `completedDates: string[]`, `startDate?: string` (earliest
     cell), `weeks?: number` (default 52 -- full GitHub-style year,
     decided 2026-09-27).
   - GitHub-style: columns = weeks, rows = weekdays (Sun-Sat), 5
     intensity levels (0 / 1 / 2-3 / 4-6 / 7+ completions -- daily
     habits cap at 1/day, but the level function is data-driven).
   - Month labels above columns; today outlined; `title` tooltip with
     date + "completed"/"no completion".
   - Grid rendered with divs + CSS grid (no canvas); respects the
     reduced-motion/design tokens (colors from CSS variables, like the
     existing calendar modal).
6. `HabitsModal.svelte`: add a habit detail state -- clicking a habit
   row opens a detail pane (inside the modal) showing the stats bar
   (current / longest streak, total completions, last completed) and
   the heatmap. Back-to-list affordance; Esc handled by the modal as
   today.
7. Storybook stories for `HabitHeatmap` (empty, sparse, dense,
   long-streak fixtures) and an updated `HabitsModal.stories.ts`.

## Slice 2 -- "make recurring" toggle in task detail

Server:

1. `shared`: `AdoptTaskAsRecurringInput` (taskId + schedule:
   frequency, interval, daysOfWeek, dayOfMonth, startTime,
   endDate, rollover) + `AdoptTaskAsRecurringResult`
   (`{ recurringTask: RecurringTask; tasks: Task[] }` -- the adopted
   task plus newly generated instances, so the client can ingest them
   in one shot).
2. `RecurringTaskService.adoptTaskAsRecurring(taskId, schedule)`:
   - Load the task (404 if missing); reject if it already has a
     `recurringTaskId` (409).
   - Create the template: text/notes/tags/startTime from the task,
     `startDate = task.date ?? today`.
   - Stamp the task: set `recurringTaskId` + `instanceDate = date`.
   - Generate instances for (startDate, startDate + 90d) skipping
     the adopted date, mirroring the create-and-generate path.
   - Broadcast the template + tasks over WS like the existing
     generate endpoint does.
3. Route `POST /api/recurring-tasks/adopt` + OpenAPI path/schema +
   Bruno tests (adopt, adopt already-recurring 409, adopt missing
   task 404, adopt validation error).
4. Unit tests in `RecurringTaskService.test.ts` + repository contract
   coverage if the stamping needs repo support (`findByRecurringTaskId`
   already exists; task stamping goes through the normal task repo
   update).

Client:

5. `TaskDetailModal.svelte`: a "Make recurring" disclosure (only when
   `task.recurringTaskId === null`) that reveals a compact schedule
   form -- reuse the HabitsModal form shape. Extract the schedule form
   (frequency/interval/days-of-week/day-of-month/startTime) into a
   shared `HabitScheduleForm.svelte` used by both modals so the two
   forms cannot drift.
6. `recurringTaskService`/`recurringTaskStore`: `adopt(taskId,
   schedule)` client call; on success ingest tasks into `taskStore`,
   show a notification ("Task is now a habit"), close the disclosure.
7. Stories + unit tests for the toggle states.
